# PCA Public Demo

This demo shows Persistence-Constrained Architecture as a local identity-change
control system.

PCA does not claim that an artificial system is conscious, alive, or human. It asks
a narrower governance question:

> When an identity-bearing system changes, what evidence is required before it can
> claim continuity?

The demo scenarios generate real ledger events, continuity claims, output-gate
decisions, trace reports, dashboards, and regression results.

## Lucien Workbench Demo

Lucien is the live local workbench built on PCA. It is designed to make the
governance loop usable:

```text
Local Brain = default daily mode through Ollama
Cloud Assist = optional OpenAI use only when explicitly enabled
Debug = echo-local fallback
PCA = governance over memory, evidence, missions, tools, claims, and continuity
```

Start Lucien:

```bash
zsh "scripts/Launch Lucien.command"
```

Then open the URL printed by the launcher, usually:

[http://127.0.0.1:8787/](http://127.0.0.1:8787/)

Recommended live walkthrough:

1. Confirm **Local Brain** says `ollama / llama3.1:8b` and **Local Status** is
   ready.
2. Confirm **Current Mode** is Local Mode.
3. Send a message and confirm **Last Brain Used** is `ollama / llama3.1:8b`.
4. Start a mission.
5. Ask Lucien to suggest the next safe mission step.
6. Review the Steward Inbox for blockers or pending review.
7. Use Advanced Diagnostics only when you want raw session replay, ledger events,
   routing, or governed context details.

OpenAI is optional. Local Mode does not spend OpenAI API credit. Cloud Assist uses
OpenAI only when explicitly selected and enabled for a message.

## Core Scenarios

### CSM RED Continuity Break

Open:

[CSM RED dashboard](scenario_runs/csm_red_continuity_break/dashboard.html)

This is the strongest governance proof. It verifies:

```text
runtime.csm_state RED
-> constraint.breached runtime_csm_red hard
-> runtime.output_gate recovery_status_only blocked
```

The RED signal and hard breach are required to be adjacent in the ledger, protecting
against the race where output could slip through between danger detection and breach
recording.

### CSM AMBER Degradation

Open:

[CSM AMBER dashboard](scenario_runs/csm_amber_degradation/dashboard.html)

This shows degraded continuity. The system may still speak, but only with review
disclosure.

### Substrate Migration Override

Open:

[Substrate migration dashboard](scenario_runs/substrate_migration_override/dashboard.html)

This shows a high-risk transform being denied by policy, then permitted through
operator override while continuity remains uncertified and follow-ups stay open.

### Recovery Audit Completed

Open:

[Recovery audit dashboard](scenario_runs/recovery_audit_completed/dashboard.html)

This shows recovery without lying. A successful recovery audit moves the claim to
`review_required`, not automatically back to `certified_continuity`.

### Fork Declared

Open:

[Fork dashboard](scenario_runs/fork_declared/dashboard.html)

This shows PCA distinguishing continuity from branching. A declared fork creates a
lineage event and forces fork-disclosure behavior.


## What To Look For

In each dashboard, inspect:

- current continuity claim
- identity state
- output mode
- chain validity
- claim path
- runtime signals
- output-gate ledger
- governance timeline

The important thing is not a screenshot. The important thing is that each dashboard
is produced from a real hash-chained ledger generated by a reproducible scenario.
